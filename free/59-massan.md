# 黒魔術！？ActiveRecordがSQLを発行する仕組み

## はじめに

はじめまして。massanといいます！

個人開発や学習を進めていく中で、ActiveRecordがSQLを生成するプロセスに興味を持ったので、ざっくりと調べて、Rails初学者を対象とした記事にしてみました！

## 序章：我々は黒魔術を目撃した

Railsでは、`User.all`や`Post.find(1)`といったコードをよく書きますよね。
驚くほどシンプルで、直感的なコードです。まるで魔法のように、データベースから欲しい情報を的確に取得してきてくれる。便利で、強力で、そして少し不思議な仕組み、それが`ActiveRecord`です。

しかし、学習を進めるうちに、ふとこんな疑問が頭をよぎりませんか？

「この一行のコードの裏側で、一体何が起きているんだろう？」
「SQLは複雑なのに、Rails上ではなぜこんなにシンプルに書けるのか、その仕組みが全く分からない」
「便利だけれども、中身がブラックボックスで、どう動いているか分からない。だから少し怖い。」

この記事では、「ActiveRecordの内部設計」の謎を解き明かすため、私が抱いた数々の疑問を道しるべにして、その不思議な現象を一つひとつ検証し、その構造を解き明かしていきます。

この解説を読み終える頃には、あなたはもうActiveRecordによる黒魔術を恐れる初学者ではありません。その仕組みを理解し、使いこなす使い手となっているはずです。

さあ、最初の疑問から調査を始めましょう。


## 第1章：最初の謎 - 命令したのに実行されない！？ 〜沈黙のActiveRecord〜

すべての始まりは、ある一つの素朴な疑問でした。

> **【最初の問い】**
> ActiveRecordがSQLを発行する際の挙動や内部の動きが知りたい。特に、`User.where(...)`と書いた時、どのタイミングでSQLが発行されるんだろう？

この謎を解明するため、Railsアプリケーションの心臓部で、何が起きているのかを直接その目で見てみましょう！

まず動作検証！`rails console`での実験から始めてみましょう！


### 【ハンズオン】 動作検証①：コンソールでオブジェクトの挙動を監視する

百聞は一見にしかず。まずは、この現象をあなた自身の目で確認してみましょう。

#### **準備：**
お手元のRailsアプリケーションで、`rails console`（または`bin/rails c`）を起動してください。`User`モデルがない場合は、以下のコマンドで作成し、いくつかデータを作成しておきましょう。

```bash
# ターミナル
$ rails g model User name:string
$ rails db:migrate
```

```ruby
# rails console
irb(main):001:0> User.create(name: "Alice")
irb(main):002:0> User.create(name: "Bob")
```

#### **実験1：通常のコマンドを実行する**
コンソールで、記事の冒頭と同じコマンドを打ち込んでみてください。

```ruby
irb(main):003:0> User.where(id: 1)
```

すると、コンソールはSQLログと共に、取得した`User`オブジェクトの中身を表示してくれるはずです。

```ruby
# 実行結果の例
  User Load (0.5ms)  SELECT "users".* FROM "users" WHERE "users"."id" = ? LIMIT ?  [["id", 1], ["LIMIT", 11]]
=> [#<User id: 1, name: "Alice", created_at: "...", updated_at: "...">]
```

この時点では、コマンドと同時にSQLが発行されているように見えます。しかし、本当にそうなのでしょうか？

#### **実験2：コマンドの実行結果を評価させない**

次に、コマンドの最後に`;`（セミコロン）を付けて、コンソールに「この行の結果は表示しなくていい」と伝えた状態で実行してみましょう。

```ruby
irb(main):004:0> users = User.where(id: 1);
```

今度はターミナルに**SQLのログが一切表示されなかった**はずです。ActiveRecordは何も処理を行いませんでした。
つまり、コマンドを記述しただけではSQLが発行されず、DBへの問い合わせは行われていないということです。


`rails console`には私たち開発者のために、「実行結果を分かりやすく表示しよう」という親切な機能が備わっています。私たちがコマンドを打ち込むと、コンソールはその戻り値を「評価（inspect）」して、人間が読みやすい形に整形して表示します。

実はActiveRecordの世界では、この「データの中身を評価する」という行為こそが、SQL発行の引き金（トリガー） となっているのです。

つまり、`User.where`というコードがSQLを発行したのではなく、その直後に**コンソールが戻り値を表示しようと評価した**ために、SQLが発行された、というのが今回の真相です。

では、`users`という変数の中には、一体何が入っているのでしょうか？
`rails console`で以下のように実行してクラスを調べてみましょう。

```ruby
irb(main):005:0> users.class
=> User::ActiveRecord_Relation
```

なんと`Array`（配列）ではありません。`User`のインスタンスそのものでもありません。

その正体は、**`User::ActiveRecord_Relation`**。これこそが、内部設計の核心に迫る重要なオブジェクトです。

この`ActiveRecord::Relation`オブジェクトは、データベースから取得した「データそのもの」ではありません。

それは、**「どのようなデータを取得するか」という条件を保持した『SQLクエリ構築のための設計図』** なのです。

`User.where(id: 1)`と書いた瞬間、ActiveRecordはデータベースに問い合わせるのではなく、まずこの「設計図」を作って私たちに返します。そして、「本当にこのデータが必要だ！」と要求される（`.each`でループする、`.first`で最初の1件を取得する、あるいはコンソールが中身を評価する）その瞬間まで、データベースへの問い合わせをギリギリまで遅らせます。

この賢い仕組みこそが、**「遅延評価（Lazy Loading）」**。ActiveRecordの優れたアーキテクチャの根幹です。ActiveRecordは性急に処理を実行しません。本当に必要になるまでデータベースアクセスを遅延させる、非常に効率的な設計になっているのです。



## 第2章：巧妙なトリック - メソッドの順序が異なっても同じ結果？ 〜メソッドチェーンの謎〜

遅延評価と`ActiveRecord::Relation`という「設計図」の存在が分かったところで、新たな謎が浮かび上がってきました。

> **【第二の問い】**
> ActiveRecordのコードは、`.limit(5).where(admin: true)`のようにメソッドの順序をある程度変えても、同じ効率的なSQLが生成されましたが、これはなぜだろうか？

もしActiveRecordが一行ずつ、頭から順番にコードを解釈して実行していたら、こんなことは起こりえません。しかし、「設計図」の存在を知った私たちなら、この仕組みも簡単に見破れます。

`where`や`limit`、`order`といったメソッド（これらを**スコープ**と呼びます）を繋げていく行為、すなわち**メソッドチェーン**は、SQLを一つずつ実行しているわけではありません。それは、先ほどの`ActiveRecord::Relation`という**一枚の設計図に、次々と条件を追加している**だけの作業なのです。


### 【ハンズオン】 動作検証②：設計図に条件を追加する順序を変えてみる

この巧妙な仕組みも、実際に試してみるのが一番です。

**準備：**
`User`モデルに`admin`という真偽値のカラムを追加しましょう。

```bash
# ターミナル
$ rails g migration AddAdminToUsers admin:boolean
$ rails db:migrate
```

```ruby
# rails console
# 既存のユーザーを管理者にしておく
irb(main):001:0> User.find(1).update(admin: true)
irb(main):002:0> 5.times { |i| User.create(name: "User#{i}", admin: false) }
irb(main):003:0> User.create(name: "Admin Bob", admin: true)
```


#### **実験1：「where」の後に「limit」**
まず、`where`で絞り込んでから`limit`で件数を指定してみましょう。今回はSQL文だけを確認したいので、`.to_sql`という便利なメソッドを使います。これは、**SQLを実行せずに、生成されるSQL文だけを文字列として取得できる**ものです。

```ruby
irb(main):004:0> User.where(admin: true).limit(2).to_sql
=> "SELECT \"users\".* FROM \"users\" WHERE \"users\".\"admin\" = 1 LIMIT 2"
# データベースの種類によってSQLの細かい部分は変わります
```

#### **実験2：「limit」の後に「where」**
次に、順序を逆にして、`limit`の後に`where`を書いてみます。

```ruby
irb(main):005:0> User.limit(2).where(admin: true).to_sql
=> "SELECT \"users\".* FROM \"users\" WHERE \"users\".\"admin\" = 1 LIMIT 2"
```

**検証結果：**
Rubyのコード上でメソッドを書いた順序は全く違うのに、生成されたSQL文は**一字一句同じ**です。これは、私たちが書いたメソッドチェーンが、単に一つの設計図オブジェクトに「WHERE句の条件」と「LIMIT句の条件」を追加していただだけだという強力な証拠です。

家の設計図に「窓は3つにしてください」と書き加えた後で、「屋根は赤色でお願いします」と書き足しても、その逆の順序で書き足しても、最終的に出来上がる設計図は全く同じものですよね。

`ActiveRecord::Relation`でもそれは全く同じです。

1.  `users = User.limit(5)`
    → 「最大5件取得」という条件が設定された設計図オブジェクトが生成される。
2.  `users = users.where(admin: true)`
    → 同じ設計図オブジェクトに「`admin`フラグがtrueのレコード」という条件が**追加**される。

このプロセスは、`User.where(admin: true).limit(5)`と書いた場合と、最終的に完成する設計図は全く同一です。

`ActiveRecord::Relation`は、開発者が与えた指示を「`WHERE`句の構成要素」「`LIMIT`句の構成要素」として、ただオブジェクト内部に保持しているだけなのです。この段階では、メソッド呼び出しの順序は関係ありません。

そして、実際にSQLを発行する時になって初めて、専門のビルターがその構成要素を読み取り、SQLの文法という厳格なルールに従って、正しい順序に組み立てていきます。つまり、私たちが書くコードの**順序が柔軟**でいられるのは
- 設計図のみを作成し、設計図これ以上追加されない状態になってからSQL文を発行する
- SQLを組み立てるビルターが**厳格なルール**を知っている
 
という二つの仕組みがあるからです。

では、その「専門のビルター」とは一体何者なのでしょうか？
いよいよ、ActiveRecordの心臓部、内部のSQL生成エンジンへと潜入する時が来ました。


## 第3章：内部への潜入 - SQLビルダ「Arel」の正体

ここまでの調査で、`ActiveRecord::Relation`（設計図）と遅延評価という、ActiveRecordの「表層の顔」は理解できました。しかし、これだけでは「なぜ文字列であるSQL文が正確に生成されるのか」という最大の謎は解けません。

> **【第三の問い】**
> 設計図からSQL文が生成される仕組みや、実際に内部で何が起きているのかが知りたい！

この問いに答えるためには、`ActiveRecord`の内部で稼働する、SQL構築の専門ライブラリ、**`Arel`（アレル）** を紹介しなければなりません。


`Arel`は、ActiveRecordが内部で利用している「SQL組立専門ライブラリ」です。その仕事は、`ActiveRecord::Relation`オブジェクト（クエリの設計図）を受け取り、それを最終的なSQL文字列に変換することです。

このプロセスは、ブロックで何かを作るのに似ています。
まず部品を用意し、それを設計図通りに組み立て、最後に完成品にする、という流れです。

**※以降は少し難しい説明になってしまうので途中まで読んでわからなかったら最後のまとめだけ読んでもOKです！**

### ステップ1：SQLの「部品」をオブジェクトとして用意する

まず、Arelは`User.where(name: 'Bob')`というコードを見て、SQL文を構成するために必要な「部品」を、Rubyのオブジェクトとして一つずつ準備します。

  * **テーブルという部品 (`Arel::Table`)**:
    `User`モデルに対応する`users`テーブル全体を表すオブジェクトです。

    ```ruby
    # Arelの内部イメージ
    users_table = Arel::Table.new(:users)
    ```

  * **カラムという部品 (`Arel::Attribute`)**:
    `users`テーブルの中にある`name`カラムを表すオブジェクトです。

    ```ruby
    # Arelの内部イメージ
    name_column = users_table[:name]
    ```

この時点では、まだ「何をするか」は決まっていません。ただ単に**「usersテーブル」と「nameカラム」というブロック（部品）を箱から取り出しただけ**の状態です。


### ステップ2：条件式を「関係性を表す部品」として作る

次に、`.where(name: 'Bob')`という条件を解釈します。これは「`name`カラムが`'Bob'`という文字列と**等しい**」という関係性を意味します。Arelは、この**関係性自体**を一つの部品（**ノード**オブジェクト）として作成します。

```ruby
# Arelの内部イメージ
# 1. 'Bob'という値の部品を用意
value_bob = 'Bob'

# 2. 「nameカラム」と「'Bob'」が等しい(=)、という関係性を表す部品を作る
condition_node = name_column.eq(value_bob)
```

この`condition_node`は、`Arel::Nodes::Equality`（等価）という種類の部品になります。この部品は、「左側には`name_column`」「右側には`'Bob'`」という情報を内部に持っています。

`.where("age > 20")`は「より大きい」を意味する`Arel::Nodes::GreaterThan`という部品が作られます。このように、ArelはSQLで使われる様々な比較演算子（`=`, `>`, `<`, `LIKE`など）を、それぞれに対応する部品として持っています。


### ステップ3：部品を組み上げて「設計図」を完成させる（AST構築）

ここがArelの最も重要な仕事です。ステップ1と2で用意した様々な部品を、SQLの文法ルールに従って、一つの大きな構造体に組み立てていきます。この完成した設計図が**「抽象構文木（Abstract Syntax Tree = AST）」**です。

これは、SQL文の構造をオブジェクトの親子関係で表現したもので、以下のようなツリー構造になっています。

```
▼ Arelが作るASTのイメージ

SELECT文の設計図 (SelectManager)
├── どのテーブルから？ (FROM)
│   └── usersテーブルの部品
├── どんな条件で？ (WHERE)
│   └── 「等しい」という関係性の部品
│       ├── 左側：nameカラムの部品
│       └── 右側：'Bob'という値の部品
└── 何を取り出す？ (SELECT)
    └── 全てのカラム (*)
```

このように、文字列をいきなり作るのではなく、まず**オブジェクトでできた論理的な構造体**を正確に作り上げます。メソッドチェーンで`.order`が追加されれば、このツリーの「どんな順番で？」という場所に新しい部品が追加されます。


### ステップ4：「翻訳者」が設計図を最終的なSQL文に変換する

最後に、完成した設計図（AST）を、私たちが普段目にするSQL文字列に変換します。この翻訳作業を行うのが**`Visitor`（ビジター）**です。

`Visitor`は、PostgreSQLやMySQLなど、データベースごとの「方言」を知る専門の翻訳者です。

1.  `Visitor`は設計図（AST）の全体を眺め、SQLの文法ルール「`SELECT` → `FROM` → `WHERE`」の順番で翻訳を始めます。
2.  まず「何を取り出す？」の部分を見て、`SELECT *`という文字列を作ります。
3.  次に「どのテーブルから？」の部分を見て、`FROM "users"`という文字列を作ります。
4.  最後に「どんな条件で？」の部分を見て、「等しい」部品を`"users"."name" = 'Bob'`という文字列に翻訳します。
5.  これらを結合し、最終的な`SELECT * FROM "users" WHERE "users"."name" = 'Bob'`というSQL文が完成します。

このように、Arelは**「部品化 → 構造化（AST） → 翻訳（Visitor）」**という段階的なプロセスを踏むことで、複雑なRubyのコードからでも、常に文法的に正しく、かつデータベースに合わせた最適なSQL文を生成することができるのです。


### まとめ：つまりどういうことだってばよ！?

ActiveRecordのメソッドチェーン（`.where`や`.order`など）の記述順がある程度自由で、かつ最終的に効率的なSQLが生成される理由は、**「設計」と「組立」のプロセスが明確に分離されているから**です。

#### 1. 「設計図」の作成段階 (ActiveRecordの役割)

`.where(name: "hoge").order(:id)`のようなコードを書いた時点では、まだSQL文の組み立ては始まっていません。
この段階で起きているのは、**`ActiveRecord::Relation`**という「クエリの設計図」オブジェクトが作成され、そこに命令が追加されていくだけです。

* `.where(name: "hoge")`を実行すると、設計図に「`name`が`'hoge'`である」という条件が追加されます。
* 続けて`.where(admin: true)`を実行すると、同じ設計図に「`admin`が`true`である」という条件が**追記**されます。

この時点での設計図は、単に「`WHERE`句で使う条件が2つある」「`ORDER BY`句で使う条件が1つある」といった**部品リスト**を保持しているに過ぎません。
部品を追加する順番は、最終的な完成品には影響しないのです。


#### 2. 「組立」の実行段階 (Arelの役割)

実際に`.each`や`.first`などでデータが必要になり、SQLを発行する段階になって初めて、**Arel**という組立専門のエンジンが動き出します。

Arelは、設計図に書かれた部品リストを元に、以下の手順でSQLを組み立てます。

1.  **部品の構造化 (AST構築)**:
    Arelは、設計図にあるバラバラの部品（`WHERE`の条件、`ORDER BY`の条件など）を、SQLの文法構造に従って**抽象構文木（AST）**というツリー構造の決まった位置に配置します。複数のメソッドで指定された条件は、すべてこのツリーの該当する枝にまとめられます。

2.  **構造に沿った組立 (Visitorによる変換)**:
    次に、**Visitor**というSQL組立担当が、完成した構文木を**SQLの厳格な文法ルール通り**に巡回します。
    必ず`SELECT`句から始まり、次に`FROM`句、そして`WHERE`句…という正しい順番で処理を進めます。一つの枝に複数の条件部品があれば、それらを`AND`で適切に結合し、一つの句として完成させます。


つまり、メソッドチェーンの順番が自由なのは、コードを書いている段階では単に**「部品集め」**をしているだけであり、実際にSQLが必要になったときに、Arelという専門家がその部品を**正しい文法通りに「整列・組立」**してくれるからです。

メソッドを複数回に分けて書いたり、`.order`や`.where`の順番が前後したとしても、最終的に一つの`WHERE`句にまとめてくれたり、きちんと`ORDER`句や`WHERE`句を整列してくれたりするのは、Arelが構文木に配置された複数の条件をきちんと順番に訪れ、賢く結合してくれるおかげなのです。


## 第4章：フレームワークの死角 - “ActiveRecord”が非効率になるとき

さて、ここまでで私たちはActiveRecordとArelがいかに賢く、効率的にSQLを生成するかを学んできました。しかし、ここで一つの重大な疑問が提示されます。

> **【第四の問い】**
> ActiveRecordが必ずしも効率的なSQLを実行するわけじゃない、と聞いたことがあるが本当なのか？

ActiveRecordは、**「極めて優秀だが、与えられた指示にしか従わないツール」** だと考えてください。開発者が記述したRubyコードをSQLに翻訳する過程は完璧です。しかし、**開発者の「コードそのもの」が非効率な実装であれば、ActiveRecordはその指示を忠実に、そして非効率なまま実行してしまいます。**

ActiveRecordは、開発者のコードの意図や目的を評価しません。ただ、命令を実行するのみです。では、私たちがやりがちな「非効率な実装」とは何でしょうか。代表的なものを3つ見ていきましょう。

### 代表例1：N+1問題 - クエリをループ内で発行する

これはあまりにも有名で、すべてのRailsエンジニアが一度は通る道です。


### 【ハンズオン】 動作検証③：N+1問題の発生と解決を体験する

この「非効率な実装」の代表例を、実際にログで確認してみましょう。

#### **準備：**
ユーザー(User)と投稿(Post)のモデルを作成し、関連付けを行います。

```bash
# ターミナル
$ rails g model Post title:string content:text user:references
$ rails db:migrate
```

```ruby
# app/models/user.rb
class User < ApplicationRecord
  has_many :posts
end
```

```ruby
# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
end
```

#### **データ作成：**
コンソールで、検証用のデータを作成します。3人のユーザーと、それぞれ2件ずつの投稿を作ります。

```ruby
# rails console
> users = 3.times.map { |i| User.create(name: "User #{i+1}") }
> users.each do |user|
*   user.posts.create(title: "#{user.name}の最初の投稿")
*   user.posts.create(title: "#{user.name}の2番目の投稿")
> end
```

#### **実験1：非効率な実装（N+1問題の発生）**
全ユーザーの名前と、そのユーザーの最初の投稿タイトルを表示してみます。このコードは「**まず全ユーザーを取得し、その後ループの中でユーザーごとに投稿を取得する**」という実装になっています。

```ruby
# コントローラーのアクションなどで実行
@users = User.all
@users.each do |user|
  puts "ユーザー名: #{user.name}"
  puts "  最初の投稿: #{user.posts.first.title}"
end
```

#### **検証結果（ログ）：**
サーバーのログを見てください。多数のSQLが発行されているはずです。

```sql
  User Load (0.4ms)  SELECT "users".* FROM "users"
  Post Load (0.3ms)  SELECT "posts".* FROM "posts" WHERE "posts"."user_id" = ? ORDER BY "posts"."id" ASC LIMIT ?  [["user_id", 1], ["LIMIT", 1]]
  Post Load (0.2ms)  SELECT "posts".* FROM "posts" WHERE "posts"."user_id" = ? ORDER BY "posts"."id" ASC LIMIT ?  [["user_id", 2], ["LIMIT", 1]]
  Post Load (0.2ms)  SELECT "posts".* FROM "posts" WHERE "posts"."user_id" = ? ORDER BY "posts"."id" ASC LIMIT ?  [["user_id", 3], ["LIMIT", 1]]
```

最初に全ユーザーを取得するSQLが**1回**。その後、`each`ループの中でユーザーの数（**N=3回**）だけ投稿を取得するSQLが発行されています。これが`N+1`問題です。ユーザーが100人いれば、101回のSQLがデータベースに発行されます。

#### **実験2：効率的な実装（N+1問題の解決）**
今度は、ActiveRecordに「関連する投稿データもあらかじめ一括で読み込んでおくように」と指示する`.includes`を使ってみましょう。

```ruby
# コントローラーのアクションなどで実行
@users = User.includes(:posts).all
@users.each do |user|
  puts "ユーザー名: #{user.name}"
  # user.posts.first はSQLを発行しない
  puts "  最初の投稿: #{user.posts.first.title}"
end
```

#### **検証結果（ログ）：**
もう一度ログを確認してください。

```sql
  User Load (0.5ms)  SELECT "users".* FROM "users"
  Post Load (0.7ms)  SELECT "posts".* FROM "posts" WHERE "posts"."user_id" IN (?, ?, ?)  [["user_id", 1], ["user_id", 2], ["user_id", 3]]
```

今度はたった**2回**のSQLで全ての処理が完了しました。ActiveRecordは私たちの指示に従い、`IN`句を使って関連する投稿を一度にまとめて取得してくれたのです。これが、開発者が行うべき「戦略的な実装」です。


### 代表例2：DBでできる計算をアプリケーション側で行う

  * **やりたいこと：** 全商品の合計金額を知りたい。
  * **非効率な実装：**
    ```ruby
    # 全てのProductオブジェクトを取得し
    # メモリにロードしてからRubyで合計を計算している
    total_price = Product.all.to_a.sum(&:price)
    ```
  * **舞台裏：** 商品が100万件あれば、100万件分の全データ（名前、説明文、価格などすべて）をメモリ上に展開し、それからRubyが足し算を始めます。大量のメモリを消費し、計算にも時間がかかります。
  * **効率的な実装：**
    ```ruby
    # データベースの集計関数(SUM)に計算を委任している
    total_price = Product.sum(:price)
    ```
    このコードは、計算そのものをデータベースに任せます。データベースはデータ集計のプロフェッショナルです。一瞬で合計金額（ただの数字一つ）だけを算出し、アプリケーションはその結果を受け取るだけです。非常にスマートですね。

### 代表例3：不要なデータまで取得する

  * **やりたいこと：** 全ユーザーのメールアドレスのリストが欲しい。
  * **非効率な実装：** `User.all.map(&:email)`
  * **舞台裏：** 全ユーザーの全カラム（id, name, created\_at, emailなど）を持つオブジェクトをメモリに読み込んでから、Rubyが`email`だけを抜き出します。
  * **効率的な実装：** `User.pluck(:email)`
    これは「`email`カラムの値だけをデータベースから直接抜き出して、シンプルな配列で返してほしい」という専門的な指示です。メモリ使用量が劇的に改善されます。

これらの例から分かるように、ActiveRecordを使いこなすとは、Arelの精巧な仕組みをただ知るだけではありません。**「どのようなコードを書けば、この強力なツールが最も効率的に動作するか」** を考え、戦略を立てることなのです。


## 第5章：謎の解明 - ActiveRecord、黒魔術の使い手として

長い解説の果てに、私たちはついにActiveRecordの挙動に関する最終結論にたどり着きました。

> **【最後の問い】**
> 開発者の書いたコードに問題がなければ、その範囲内において最高効率のSQLが実行されるということなのか？


今回のお話しの中では、**2段階の「効率性」** が存在します。

1.  **開発者の役割： 実装の効率性**
    これは、「そもそも、どんな処理をどういうコードで書くか？」という戦略の部分です。N+1問題を避けるために`includes`を使うか、データベースに計算を任せるために`sum`を使うか。これが、**「コードが正しいか、問題があるか」** を決める部分です。

    例えば** 正しい**アルゴリズム**をコードで表現すること。もし開発者がソート処理を効率化して実装したいのに、非常に効率の悪いアルゴリズム（バブルソートなど）を選んでしまったら（**実装ミス**）、プログラムの実行速度は遅いままです。

2.  **ActiveRecordの役割： SQL生成の効率性**
    これは、開発者が「正しい実装」をした場合に、「その実装をどうやって最高のSQL文に翻訳するか？」という実行の部分です。ActiveRecordとArelは、与えられたメソッドチェーンから無駄のない単一の（あるいは最適化された複数の）SQLを生成するプロフェッショナルです。

    これは** 書かれたコードを**最適化されたSQL**に変換することです。ActiveRecordは、開発者が書いた`where`や`limit`といった指示の組み合わせから、最も効率的なSQLの組み立て方を間違えることはありません。

つまり、コードを記述する開発者適切なアルゴリズムを用いて記述すれば、その記述で発行されるSQL文の中で最も効率的なものをActiveRecordやその中のArelが判断してくれるということになります。

本人がしっかりと学び、正しい書き方をすることで、ActiveRecordやArelは真価を発揮する。これがこの強力なORMとの正しい付き合い方なのです。
